# Cryri Jobs

Применяй этот скилл при любой операции с Cryri Jobs. Следуй `AGENTS.md`
рабочего каталога и проекта; для кода действует `ponytail`.

## Общий реестр и принадлежность

Рабочий корень: `/Users/zoya/projects/research/ReseachOS`.
Единый реестр — `tree/cryri-jobs.json`, таблица для человека —
`tree/cryri-jobs.md`. Таблица создаётся из JSON скриптом `scripts/registry.py`;
не редактируй представление отдельно. Реестр дополняет карточки проектов.

Перед любой операцией сначала прочитай реестр. Для каждой записи нужны:
имя, точный ID/тег сервиса, комментарий запуска, проект ResearcherOS, карточка,
цель, статус, число GPU, время отправки и последней проверки. Храни источник
подтверждения принадлежности и пути к логам/телеметрии. Не храни секреты.

Если разворачиваешь роутер к моделям, сохраняй в записи `router_endpoint`
(OpenAI-совместимый base_url с `/v1`), `model` (имя модели для запросов),
`local_endpoint`, `tunnel_command` и `connection_note` (нужен ли Tailscale
или SSH-туннель). В `endpoint` остаётся адрес самой модели. Укажи требования
авторизации и место хранения ключа, если он нужен, но не значение секрета.
Обновляй эти поля при изменении адресов и состава пула. `registry.py` выводит
инструкцию подключения под таблицей в том же Markdown-файле.

Видимость в `cryri jobs` или доступ через SSH НЕ означают принадлежность
пользователю. Сверяй точный ID с квитанцией отправки, именем и комментарием.
`volovikova` обязательна **и в имени, и в комментарии**. В текущей обвязке
человеческое имя — `cloud.description` до `; comment:`, комментарий — после;
автоматический `lm-mpi-job-UUID` — технический ID, а не поле имени.
Если поля недоступны, пиши «неизвестно», не «нет». Не импортируй чужие или
неподтверждённые джобы как наши. Старые подтверждённые запуски можно внести
по реальным квитанциям; отсутствие мониторинга явно пометь как legacy.

## Отправка

1. Найди проект и существующую карточку в `tree/<project>/koi-structure/`.
   Не создавай дубликаты. Следуй `koi-execute-card`; карточка остаётся running,
   пока её вычислительное задание pending/running.
2. Оцени память: веса, точность, KV-кэш/длина контекста либо обучение,
   batch, число копий, пиковый запас и доступная память каждой GPU. Запиши
   оценку и выбранные ресурсы в карточке и квитанции.
   Если процесс потенциально требует мало GPU-памяти, может разместиться
   на меньшем ресурсе/CPU либо оценка памяти неясна — **до отправки согласуй
   с человеком** цель и ресурсы. Высокая загрузка не заменяет это согласие.
   Не отправляй такую джобу по общему «запусти эксперимент» без обсуждения.
3. Перед отправкой проверь `volovikova` в обоих полях. Используй проверенную
   проектную обвязку отправки; не переписывай её без необходимости.
4. Не ограничивай длительность pending. Не отменяй и не пересоздавай из-за
   ожидания ресурсов. Таймаут отдельного сетевого запроса не является лимитом
   ожидания джобы. Лимит выполнения — отдельное решение; не добавляй его молча.
5. По возможности оберни рабочую команду в `scripts/gpu_telemetry.py run`.
   Сбор выполняется **в GPU-контейнере**, раз в 60 секунд, через `nvidia-smi`:
   загрузка каждой GPU, использованная/полная память и UUID. Строки
   `CRYRI_GPU_SAMPLE {json}` попадают в stdout, читаемый через `cryri logs`,
   и в постоянный JSONL на общем диске. Скрипт должен быть доступен внутри
   контейнера. Не подменяй загрузку GPU длиной очереди или заполнением KV-кэша.
   Если сбор невозможен, зафиксируй почему; не заявляй, что он подключён.
6. Сразу после ответа сервиса запиши точный ID, реальные pending/running,
   имя/комментарий, ресурсы и пути в реестр **и ту же карточку/отчёт**.
   При неопределённом результате отправки сохрани квитанцию неопределённости,
   проверь список сервиса; повторная отправка без этой проверки запрещена.
7. Создай/обнови один heartbeat ожидания с интервалом **20 минут** для
   pending и неподтверждённых отмен (cancel_requested) из реестра через
   `automation_update`. На каждом запуске обновляй
   реестр и карточки. При переходе в running сообщи ID/проект и новый статус.
   Заверши этот heartbeat, когда pending и cancel_requested больше нет. Без изменений молчи.
   Ожидание не имеет срока истечения; сбой доступа не равен падению джобы.
8. Проверь наличие одного heartbeat мониторинга GPU раз в **5 часов**.
   Используй существующий, не создавай дубликаты. Автоматизация только читает
   сервис/логи и обновляет отчёты; она не отправляет и не удаляет джобы.

## Просмотр и мониторинг

Перед SSH проверь фактический алиас. Здесь алиас `cryri-jobs` может отсутствовать;
тогда используй адрес/ключ из рабочего `AGENTS.md`. На сервере запускай
`cryri` в login shell (`bash -lc`), иначе могут отсутствовать `GWAPI_ADDR/KEY`.
Не выводи окружение, ключи и `router.env`. Проверенный CLI:
`/home/jovyan/miniconda3/bin/cryri jobs --region SR006 -n 0`,
`status FULL_JOB_ID --region SR006`, `logs FULL_JOB_ID --region SR006 --raw`.

Показывай только подтверждённые записи, если пользователь спрашивает «наши».
Для операции с другими записями сначала установи принадлежность. Обновляй
статус и время проверки в реестре и карточке при каждом обнаруженном изменении.
Терминальные статусы: completed, failed, cancelled. Если сервис не даёт данных,
оставь последний подтверждённый статус и отметь ошибку/время, не выдумывай новый.
После успешного `kill` отмена может отражаться с задержкой; до подтверждения
сохраняй cancel_requested. Удаление из списка вместе с успешной квитанцией
`kill` подтверждает cancelled; одно отсутствие в списке — нет.

Каждые **5 часов** для running:

- Получи постоянный JSONL с GPU-контейнера по записанному пути, сохрани копию
  в `tree/cryri-jobs/telemetry/<job-id>.jsonl`. Не считывай `nvidia-smi`
  на CPU Jupyter и не приписывай его GPU удалённой джобе.
- Построй PNG и JSON-сводку за последние 5 часов через `gpu_telemetry.py report`,
  передавая ожидаемое число GPU. Храни в `tree/cryri-jobs/reports/<job-id>/`.
  График показывает отдельно загрузку (%) и память (GiB), по каждой GPU.
- Согласованный порог: средняя по времени загрузка **ниже 20%** за окно.
  Проверяй каждую GPU: одна простаивающая GPU не должна скрыться в среднем.
  Для вывода требуется не менее 80% покрытия 5-часового окна, актуальные
  измерения и ожидаемое число GPU. Пробелы/ошибки не считать нулями.
- При плохой загрузке сообщи пользователю ID, проект/карточку, цель, GPU,
  среднюю загрузку и память, покрытие, приложи PNG. Высокая занятая память
  не отменяет предупреждение о низкой вычислительной загрузке.
- При отсутствии/недостатке измерений сообщи «нет данных», не «простой».
  Для legacy-записей с явной пометкой об отсутствии мониторинга не присылай
  повторно одно и то же предупреждение каждые 5 часов. Не перезапускай их
  для установки сборщика без отдельного запроса.
- При нормальной загрузке и неизменном состоянии молчи. Повторное уведомление
  нужно при значимом изменении/ухудшении, новой проблеме, завершении или
  необходимости действия пользователя. Учитывай последнее уведомление в реестре.

График без измерений допустим только как график «нет данных»; не рисуй нулевую
линию. Не обещай непрерывный мониторинг, если доступна только разовая выборка.
Локальные heartbeat выполняются, пока компьютер включён и приложение работает.

## Остановка / удаление

1. Сначала реестр, затем точный ID и живой статус. Проверь привязку к проекту,
   карточке, рабочий процесс/модель, число GPU, зависимости (роутер/клиенты).
2. Получи график и сводку последних 5 часов. Если данных нет, явно укажи это;
   отсутствие данных не является основанием считать задание бесполезным.
3. Покажи короткую сводку: имя, ID, цель, проект/карточка, статус, GPU,
   память/утилизация, зависимости и что будет остановлено. Спроси:
   «Подтверждаешь остановку <точные ID>?» **Дождись ответа.**
   Применяется и к прямому запросу «удали»: пользователь отдельно потребовал
   подтверждение после этой сводки. Подтверждение относится только к показанным
   ID; не расширяй список. Автоматический монитор никогда не удаляет задания.
4. После согласия сначала исключи сервер из роутера, останови обнаружение и
   регистрацию удаляемой копии, дождись нуля активных запросов. Проверь ответ
   оставшегося сервера. Останови только согласованные ID через `cryri kill`.
   Используй проектные инструкции для зависимостей; отдельные серверы не трогай.
5. Сохрани запрос отмены и квитанцию сразу; до конечного статуса включи
   heartbeat проверки каждые 20 минут, как для pending. Подтверди терминальный статус,
   обнови реестр, ту же карточку и отчёт с результатом/причиной и артефактами.
   Сохрани историю записи. Не ставь карточку done, если другие её джобы активны.

## Помощники

```bash
# Добавить запись или обновить поля существующего ID; представление обновится.
python3 scripts/registry.py upsert --record /path/to/receipt.json
python3 scripts/registry.py render

# Внутри GPU-контейнера: память и загрузка в stdout и постоянном JSONL.
python3 gpu_telemetry.py run --run-name volovikova-project-card \
  --output /shared/runs/volovikova-project-card/gpu.jsonl -- python train.py

# На локальном компьютере после получения JSONL.
python3 scripts/gpu_telemetry.py report --input /path/to/gpu.jsonl \
  --output-dir /path/to/report --expected-gpus 2 --threshold 20
```

`registry.py` разрешает только проверенные записи с `volovikova` в обоих полях;
не используй его для классификации неизвестных чужих ID. Схема записи и
текущие реальные примеры находятся в общем JSON-реестре. У CLI `sample/run`
зависимости только из стандартной библиотеки; `report` использует matplotlib.
