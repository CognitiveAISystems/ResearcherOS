01 · Список работ

Этапы

Одни и те же фичи проходят три слоя: сначала проектирование новой реализации и дизайн, затем сервер и клиент, потом интеграционная приёмка. Установка проходит через все четыре этапа.

Этап 1 · недели 1–2

Проектирование новой реализации и модулей

На этом этапе нужно подготовить основу новой реализации, сохранив действующие архитектурные принципы ResearcherOS. Команда определяет границы модулей, единые операции для клиента и агента и способ простой поставки приложения. Код продуктовых функций на этом этапе не пишут.

  1. Инструменты и сборка. На этом подэтапе команда выбирает технологии для нового клиента и сервера и фиксирует выбор до начала разработки. Одновременно определяется, как собирать приложение, запускать автоматические проверки и передавать макеты из Figma разработчикам. Результатом должен стать воспроизводимый процесс, с помощью которого новый участник сможет собрать и проверить проект на своей машине. Этот процесс станет технической основой для реализации отдельных функций на следующих этапах.
  2. Контракты операций. Здесь нужно описать единые правила для всех изменений проекта: как система проверяет входные данные, записывает файлы, создаёт коммит по запросу и сообщает пользователю результат. Отдельные контракты нужны для работы с файлами и Git, принятия отчёта, совместного редактирования статьи, просмотра нескольких репозиториев как одного проекта и публикации проекта в Hub для чтения. Клиент и агент будут обращаться к одним и тем же операциям, поэтому поведение системы не разойдётся между интерфейсами. Эти контракты затем определят границы модулей и ожидаемые ответы сервера.
  3. Границы модулей. После согласования операций нужно распределить их между модулями новой реализации. Доменная логика задаёт правила, команды выполняют пользовательские действия, адаптеры работают с диском и Git, а HTTP-слой только принимает запросы и возвращает ответы. Такая карта нужна, чтобы не переносить структуру сегодняшнего кода в новую систему без разбора.
  4. Установка и поставка. Отдельно нужно спроектировать поставку приложения для человека, который не знает внутреннего устройства ResearcherOS. План должен определить состав установочного пакета, единый способ запуска, место для локальных настроек, порядок обновления и понятную диагностику ошибок. Файлы исследований при установке и обновлении приложения затрагиваться не должны.
  5. Результат этапа. Этап завершён, когда команда приняла архитектурные решения, описала операции и границы модулей и согласовала технический сценарий установки. Эти материалы становятся основанием для макетов и разработки, поэтому спорные места нужно закрыть до начала реализации соответствующего среза.

Этап 2 · с недели 1

Дизайн-проект системы

На этом этапе нужно сформировать целостный образ ResearcherOS и спроектировать путь человека через систему. Действующий интерфейс служит отправной точкой, но дизайн дополняет его общим настроением, сквозными сценариями, недостающими состояниями и спецификациями для разработки.

Недели 1–2 · Визуальное направление: мудборды и референсы

Сначала нужно определить, какое впечатление должна создавать система. Для этого собирают референсы, сравнивают несколько визуальных направлений и связывают выбранный образ с основными пользовательскими сценариями.

  1. Мудборды и референсы. Сначала нужно собрать визуальные референсы и проверить, какое настроение подходит ResearcherOS. В мудбордах сравниваются цвет, типографика, плотность интерфейса, характер иллюстраций и метафоры лаборатории или рабочего стола. Референсы нужны не для копирования отдельных экранов, а для выбора общего языка системы.
  2. Выбор направления. На основе мудбордов дизайнер готовит два или три направления и показывает, как каждое из них выглядит на нескольких ключевых экранах. Команда выбирает одно направление и фиксирует причины выбора, а также приёмы, которые использовать не следует. Это решение задаёт основу для светлой и тёмной тем и будущей библиотеки компонентов.
  3. Пользовательские сценарии. Параллельно нужно описать основные пути пользователя: от постановки задачи и проведения эксперимента до отчёта, вывода и статьи. Отдельные сценарии нужны для первого запуска, синхронизации через Git, разрешения конфликта и просмотра проекта в Hub. Для каждого сценария следует определить исходное состояние, действия человека и понятный результат.

Недели 3–5 · Пользовательские сценарии и ключевые окна

Затем нужно собрать интерфейс в несколько связанных потоков. Для каждого потока проектируются основные окна, светлая и тёмная темы, пустые и ошибочные состояния и режим только для чтения, если он нужен.

  1. Исследовательский цикл. В этом потоке нужно связать карту лаборатории, карточку узла, канбан, монитор прогона, отчёт и базу знаний. Пользователь должен видеть, как поставленная задача превращается в эксперимент, а принятый отчёт — в вывод исследования. Макеты должны покрывать обычный путь, отсутствие данных, ошибку и возврат к предыдущему шагу.
  2. Установка и рабочая область. Сценарий начинается с загрузки приложения и заканчивается открытым проектом. Нужно показать выбор папки с исследованиями, автоматический поиск существующих проектов, создание нового проекта и проверку окружения. Отдельно проектируются случаи, когда Git не настроен, формат проекта несовместим или запуск не удался, чтобы пользователь видел причину и следующее действие.
  3. Совместная работа и публикация. Здесь нужно показать весь путь совместной работы: человек сохраняет свои изменения, получает чужие коммиты и разрешает конфликт с понятным описанием причин и последствий. В тот же сценарий входят совместное редактирование статьи и проверка предложений агента. Отдельные макеты должны показать проект, собранный для просмотра из нескольких репозиториев, и публикацию его снимка в Hub, где данные доступны без редактирования. На каждом экране пользователь должен понимать, кто может менять данные, в каком репозитории они сохранятся и что произойдёт дальше.
  4. Дополнительные возможности. После основных потоков нужно спроектировать вспомогательные возможности. Обзор литературы помогает собирать источники, мастер-страницы дают постоянные точки входа в важные материалы, чат поддерживает обсуждение работы, лента открытий показывает новые результаты, а виджеты и разбор структуры статьи помогают следить за состоянием исследования. Все эти функции должны использовать общую навигацию и одинаково сообщать о сохранении, ожидании и ошибках. После их согласования из готовых сценариев можно собрать вводный тур по платформе, не создавая для него отдельную модель интерфейса.

Недели 4–8 · Поведение интерфейса и передача в разработку

После утверждения потоков нужно уточнить поведение интерфейса во времени и подготовить материалы, по которым разработчики смогут воспроизвести его без дополнительных догадок.

  1. Переходы. Когда состав экранов утверждён, нужно показать переходы между ними и изменение интерфейса после действий пользователя. Прототип должен объяснять, как вернуться из отчёта на доску, перейти от рабочего документа к записи в базе знаний или статье и сохранить выбранный объект при переходе между общей картой лаборатории и подробным представлением узла. Анимация должна помогать заметить изменение состояния, не замедляя основное действие. Проверенный прототип станет основой для описания состояний экранов и передачи макетов в разработку.
  2. Решения человека. Отдельно проектируются моменты, в которых система ждёт решения человека: принятие предложения агента, подтверждение удаления и выбор действия при конфликте. Интерфейс должен заранее показывать последствия и доступность отката. Ни агент, ни фоновая синхронизация не должны скрытно принимать такое решение.
  3. Состояния системы. Для каждого основного действия нужно показать ожидание, успешное сохранение, работу без сети, конфликт и ошибку. Сообщение должно объяснять, что произошло, сохранились ли данные и какое действие доступно дальше. Эти состояния используются одинаково во всех рабочих областях.
  4. Передача в разработку. Подэтап заканчивается комплектом материалов для реализации. Для каждого ключевого потока нужны макеты, интерактивный прототип, состояния экранов, связь с требованиями ROS-* и ожидаемые ответы операций. Разработчик должен иметь возможность воспроизвести сценарий без устных уточнений основной логики.

Этап 3 · недели 4–12

Разработка по принятой архитектуре

На этом этапе нужно реализовать новый сервер и клиент по принятым контрактам и макетам. Работу ведут вертикальными срезами: каждый срез включает операции, интерфейс и проверку, а клиент и агент используют один способ изменения проекта.

  1. Платформа и установка. Сначала нужно собрать приложение в единый дистрибутив и связать запуск клиента с локальным сервером. После установки ResearcherOS сам находит проекты в выбранной папке, хранит настройки отдельно от исследований и сообщает понятную причину, если открыть проект не удалось. Обновление приложения не должно менять или удалять файлы проекта.
  2. Исследовательский цикл. Следующий срез реализует путь от карты до принятого вывода. Для дерева, канбана, отчёта и базы знаний одновременно создаются серверные операции, экраны и автоматические проверки. Срез считается законченным, когда изменения сохраняются в файлах и остаются корректными после повторного открытия проекта.
  3. Обмен и составной вид. После завершения локального цикла нужно реализовать обмен изменениями через Git и режим, в котором несколько репозиториев отображаются как единое дерево проекта. Каждое изменение должно записываться именно в тот репозиторий, где хранится исходный файл. Если у пользователя есть несохранённые правки, система не должна получать чужие коммиты, пока риск потери данных не устранён; возникший конфликт нужно объяснить обычным языком и предложить безопасные действия. Для публикации в Hub создаётся зафиксированная версия проекта, доступная только для чтения.
  4. Статья. В этом срезе реализуются список статей, редактор, просмотр PDF и одновременная работа нескольких участников. Для согласования параллельных правок используется механизм CRDT, который объединяет изменения без перезаписи чужого текста. Сведения о том, кто сейчас находится в документе, хранятся отдельно и не становятся частью статьи. Зафиксированная версия попадает в Git только по явной команде пользователя, а предложение агента остаётся на проверке и не меняет основной текст до принятия. В результате статья получает управляемую историю, которую можно проверить в сценариях совместной работы.
  5. Дополнительные функции. Когда основные сценарии работают устойчиво, можно подключить обзор литературы, чат, монитор, виджеты и мастер-страницы. Чат автоматически запускает локального агента при отправке сообщения: человек может задать вопрос или поручить работу с выбранным проектом без команды или названия навыка. Итог появляется в той же панели, журнал — во вкладке по выбору человека без переключения основного экрана. Каждая функция использует общие операции сохранения и показывает те же статусы, что остальные части приложения. Если времени не хватает, этот блок сокращают раньше ядра исследования, синхронизации или статьи.
  6. Результат этапа. Этап завершён, когда все обязательные требования имеют реализацию, экран и автоматическую либо воспроизводимую ручную проверку. Установленная сборка открывает эталонный проект без ручного запуска сервера, а известные ограничения перечислены до начала приёмки.

Этап 4 · недели 10–14

Интеграционное тестирование и приёмка

На этом этапе нужно проверить собранную систему целиком на эталонном проекте и чистой машине. Недели 10–12 отводятся на интеграционное тестирование параллельно с завершением разработки. На неделях 13–14 состав функций фиксируется, команда проводит финальную приёмку и исправляет блокирующие дефекты.

  1. Интеграционное тестирование. На неделях 10–12 нужно проверить, как готовые части системы работают вместе, и устранить ошибки на границах между хранением данных, серверными операциями и интерфейсом. Повторная проверка проводится после каждого исправления, которое затрагивает несколько функций.
  2. Исследовательский цикл. На эталонном проекте нужно пройти полный путь от карты и карточки эксперимента до отчёта, вывода и статьи. После перезапуска состояние должно сохраниться, а старый проект — открыться без ручной миграции. Так проверяется совместная работа функций, которые ранее тестировались по отдельности.
  3. Совместная работа. Затем нужно проверить совместную работу с проектом. Несколько репозиториев должны корректно отображаться как единое дерево, обмен изменениями через Git должен останавливаться при несохранённых правках, а конфликт должен сопровождаться понятным выбором дальнейшего действия. Два участника должны одновременно редактировать одну статью, после чего её согласованную версию можно явно сохранить в Git. Опубликованная в Hub версия проекта должна открываться для просмотра, но не допускать изменений. Успешное прохождение этого сценария подтверждает, что локальная работа, синхронизация и публикация совместимы между собой.
  4. Установка. На чистой машине человек проходит публичный сценарий без помощи разработчика: устанавливает ResearcherOS, выбирает папку с исследованиями и открывает проект. Ему не приходится отдельно запускать сервер или вручную менять конфигурационные файлы. Повторный запуск и обновление сохраняют выбранную рабочую папку и сами исследования.
  5. Результат этапа. Приёмка завершена, когда у каждого обязательного требования есть пройденный сценарий или автоматический тест, а блокирующие дефекты закрыты. Ограничения, которые остаются в релизе, перечислены отдельно вместе с их влиянием на пользователя.

Что система должна уметь

Поведение по страницам каталога. Ссылка ведёт на визуализацию и описание образца. Требования — одно действие на строку. Пути текущего кода сюда не входят.
