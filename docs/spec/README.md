# Спецификация ResearcherOS (черновик)

Документ задаёт требования к **новой** реализации платформы.
Действующий интерфейс — интерактивный образец желаемого результата, не описание кода и не каркас, который нужно наращивать.

Витрина: [docs-site/todo/](../../docs-site/todo/).
Как писать и менять этот документ: [AGENTS.md](../../AGENTS.md), раздел «Спецификация платформы».

Статус: черновик. Принятые архитектурные решения — в `docs/adr-*.md`.

## 1. Общие сведения

ResearcherOS — среда ведения исследования рядом с кодом: дерево постановки, эксперименты, отчёты, знание и черновик статьи живут в файлах репозитория.

Этот документ — спецификация требований (SRS-lite): что система должна уметь и как это принять. Он не инвентарь текущих модулей.

## 2. Цели и не-цели

**Цели**

- Исследователь ведёт постановку, прогоны, отчёты, знание и статью в файлах проекта.
- Команда обменивается долгой историей через Git.
- Агент в редакторе ходит в те же операции, что человек, без обхода контракта.
- Новый код модульный: домен, команды, адаптеры (диск, Git), тонкий HTTP.

**Не-цели**

- Облачная база как источник истины.
- Сохранить текущую структуру кода.
- Один протокол на всё: и историю файлов, и живой набор в статье, и снимок Hub.

## 3. Ограничения (уже решено)

- Репозиторий владеет проектом. ResearcherOS читает и пишет файлы.
- Git — долгая история и обмен между копиями.
- Разбор отчёта вводит результат запуска в исследовательскую модель.
- Совместное редактирование статьи (CRDT / Yjs) — только оперативный текст открытого окна. Коммит — по явной команде.
- Hub показывает снимок только для чтения и не пишет в исходный проект.

## 4. Роли

| Роль | Что делает |
|------|------------|
| Исследователь | Правит дерево, доски, отчёты, статью в локальной копии |
| Агент в редакторе | Те же операции по контракту; предложения по статье ждут человека |
| Читатель Hub | Смотрит опубликованный снимок, не меняет исходник |

## 5. Функциональные требования

Приоритет: **must** — без этого приёмки нет; **should** — нужно в том же этапе, если не блокирует must.

У каждого требования: формулировка «система должна» и способ приёмки. Пути текущего кода сюда не писать.

### Документ проекта, страницы, отчёты

| Id | Pri | Требование | Приёмка |
|----|-----|------------|---------|
| ROS-DOC-01 | must | Система должна читать и записывать дерево, шапку проекта и доски в один канонический текстовый файл так, что повторная запись не меняет смысл текста, который пользователь не редактировал. | Эталонный проект открыть → сохранить без правок → смысл узлов и карточек тот же. |
| ROS-DOC-02 | must | Система должна хранить HTML-страницы проекта: создать, удалить, отдать файл, привязать к узлу, показать или спрятать. | Страница появляется у узла, пин виден на карте, снятие пина не удаляет файл. |
| ROS-DOC-03 | must | У карточки эксперимента должен быть Markdown-отчёт. Разбор готового отчёта переносит заявленный вердикт и выводы в состояние проекта. Перевод карточки в «готово» запускает оформление вывода, если его ещё нет. Курируемую заметку из каждого отчёта система создавать не должна. | Карточка с корректным отчётом после разбора меняет вердикт / выводы; лишней заметки в знании нет. |
| ROS-DOC-04 | must | Система должна открывать новый отчёт с пустыми разделами «Цель», «Постановка эксперимента», «Задачи», «Эксперименты», «Результаты», без внутренних инструкций агенту. | Новая карточка открывается с пятью незаполненными разделами. |
| ROS-DOC-05 | must | Система должна позволять редактировать блоки отчёта в одном документе без переключения Write/View, сохранять изменения автоматически и показывать состояние сохранения. | Изменить абзац, перейти к следующему и повторно открыть отчёт; текст сохранён, остальные блоки остаются оформленными. |

### Слияние репозиториев и обмен

| Id | Pri | Требование | Приёмка |
|----|-----|------------|---------|
| ROS-MERGE-01 | must | Несколько проектов с общим идентификатором система должна читать как одно дерево. Совпадение узлов — по типу, нормализованному заголовку и родителю. Запись уходит в репозиторий-владелец. Общего хранилища нет. | Два репозитория с общим id открываются как одно дерево; правка узла попадает в файл владельца. |
| ROS-MERGE-02 | must | Конфликт (два текста на одном месте, грязное дерево, отказ слияния) система должна объяснить человеку понятной причиной, не сырым выводом Git. | На эталоне с конфликтом UI/API показывает одну причину. |
| ROS-SYNC-01 | must | Правка клиента или агента: проверить правила → записать файлы → решить, нужен ли коммит → вернуть статус (на диске / в очереди на отправку / конфликт). | После правки узла статус однозначен; повтор той же операции не плодит лишний коммит. |
| ROS-SYNC-02 | must | Обмен между машинами идёт через Git (исследовательская ветка). Отправка не проходит, если в исследовательском дереве есть незаписанные правки. После получения чужих коммитов система умеет показать новые выводы. | Pull при грязном дереве отвергается; после чистого pull новые выводы видны в ленте. |

### Канбан и дерево

| Id | Pri | Требование | Приёмка |
|----|-----|------------|---------|
| ROS-KANBAN-01 | must | У узла-владельца есть доска: колонки, карточки, порядок (перетаскивание и сортировка по дате, тегу, зависимостям). У карточки — заголовок, описание, теги, зависимости, время. | Порядок после перетаскивания сохраняется в файле и виден после повторного открытия. |
| ROS-KANBAN-02 | should | Второй вид доски — граф зависимостей с сохранённой раскладкой. Живой монитор прогона доступен, если у карточки заданы источники лога и метрик. | Ребро на графе переживает перезагрузку; монитор открывается у карточки «в работе» с заданными источниками. |
| ROS-TREE-01 | must | Дерево любой глубины. Тип узла — роль, не уровень заголовка. Канбан — свойство узла, не привилегия одного зашитого типа. Циклы запрещены. | Можно добавить вложенность глубже четырёх уровней, сохранить, открыть в другом клоне после обмена через Git. |
| ROS-TREE-02 | must | Цепочка «проблема → причина → доказательство или гипотеза устранения → метод» допустима как частный случай, чтобы открыть уже существующие проекты без ручной миграции. | Эталонный старый проект открывается с тем же смыслом узлов и досок. |

### Знание, литература, статья, оболочка

| Id | Pri | Требование | Приёмка |
|----|-----|------------|---------|
| ROS-KNOW-01 | must | Вопросы и выводы хранятся отдельно от дерева, с лимитом на метод. Автосводки знания пересобираются из состояния проекта; ручные заметки система не затирает. | После вывода по карточке сводка обновляется; файл ручной заметки на месте. |
| ROS-LIT-01 | should | Обзор литературы (локальная библиотека, внешние источники, наборы, очередь), разбор структуры статьи и вехи метода — отдельные функции с тем же правилом записи и отправки, что у дерева. | Набор обзора и веха переживают сохранение и обмен через Git. |
| ROS-PAPER-01 | must | Пока статья открыта, несколько человек правят один текст через CRDT. Обновления собираются в пакеты. Присутствие (курсор) не смешивается с текстом. На диск документ сбрасывается пачками и по команде «сохранить». Коммит — только по явной команде. | Два участника на общей Git-базе видят чужой набор; коммита без команды нет. |
| ROS-PAPER-02 | must | Если базовые версии Git разошлись, обмен текстом останавливается и объясняется. Независимые истории система не склеивает молча. Предложение агента не входит в основной текст без решения человека. | Разный HEAD — понятная остановка; предложение остаётся на ревью. |
| ROS-SHELL-01 | should | Система предоставляет чат и очереди задач агента, автопрогон карточки, панели-виджеты и три масштаба лаборатории (вся / программа / один проект). | Каждый контур открывается из оболочки и пишет только через общие операции. |
| ROS-SHELL-02 | must | Система должна позволять человеку установить и запустить ResearcherOS, найти или создать проект и открыть его без ручного запуска сервера или редактирования конфигурации. Установка, обновление и удаление приложения не изменяют файлы исследования. | На чистой машине человек устанавливает приложение, выбирает папку с исследованиями и открывает проект; после обновления проект и настройки доступны. |
| ROS-CHAT-04 | must | При отправке сообщения система должна автоматически запускать доступного локального агента с контекстом выбранного проекта. Обычный чат принимает вопросы и поручения на работу без команды или названия навыка: агент может изучать и изменять файлы проекта, а на вопросы о полученных результатах опирается на базу выводов и отчёты. Система показывает состояние выполнения и возвращает итог в тот же чат. Журнал запуска доступен во вкладке приложения по выбору человека; основной экран не переключается. | Отправить вопрос по выводам и поручение изменить файл без настройки Inbox и без команд; увидеть ответ, выполненную правку и журнал, оставаясь в приложении. |
| ROS-CHAT-05 | must | Система должна запускать из отчёта интервью по всей постановке по скиллу koi-grill-experiment через команду \agent, кнопку или действие над выделением. Агент задаёт по одному вопросу с рекомендацией; история привязана к карточке. После интервью и ревью человек применяет предложенные цель, постановку и задачи. | Начать интервью, ответить, закрыть и открыть карточку; история доступна. Применение предложения заполняет три раздела и сохраняет эксперименты и результаты. |
| ROS-HUB-01 | must | Опубликованный снимок доступен только для чтения и не изменяет исходный проект. | В режиме Hub нет успешных операций записи в исходник. |

## 6. Качества

| Id | Pri | Требование |
|----|-----|------------|
| ROS-Q-01 | must | Сервер состоит из модулей с границами: домен → команды → адаптеры → HTTP. Модуль пишет файлы проекта или коммит, не свою скрытую базу. |
| ROS-Q-02 | must | Клиент и агент используют один набор операций. Тихая запись в обход модуля запрещена. |
| ROS-Q-03 | must | На своей копии репозитория работа возможна без сети, кроме обмена через Git и комнаты статьи. |
| ROS-Q-04 | should | Служебное состояние среды выполнения не входит в репозиторий исследования. |

## 7. Интерфейсы

- Файлы Research Project (дерево, отчёты, страницы, знание, статья, виджеты).
- HTTP API локального сервера.
- Комната статьи (CRDT); signaling не носит текст статьи как источник истины.
- Git (исследовательская ветка).
- Клиент: Vue или React — выбор фиксируется в начале части «клиент» и не меняется по ходу.
- Макеты экранов — отдельный этап; они не подменяют требования этого документа.

## 8. Состав работ

Интерактивный план (диаграмма Ганта, четыре месяца и недели 1–14): [docs-site/todo/](../../docs-site/todo/).

1. **Недели 1–2. Проектирование новой реализации и модулей.** Базовые принципы архитектуры сохраняются. Результат: ADR, каталог операций, карта модулей, контракты и технический проект простой поставки.
2. **Недели 1–8. Дизайн-проект.** Визуальное направление, мудборды и референсы (1–2); пользовательские сценарии и ключевые окна, включая установку и первый запуск (3–5); поведение интерфейса и передача в разработку (4–8).
3. **Недели 4–12. Разработка по принятой архитектуре.** Сервер с недели 4, клиент и поставка с недели 5. Вертикальные срезы: платформа и установка; исследовательский цикл; обмен и Hub; статья; дополнительные контуры.
4. **Недели 10–14. Интеграционное тестирование и приёмка.** Недели 10–12 отведены на совместную проверку готовых частей системы, недели 13–14 — на фиксацию состава функций, финальную приёмку и исправление блокирующих дефектов.

## 9. Приёмка

- У каждого `ROS-*` — сценарий из таблицы или автотест.
- Золотой проект: карта → карточка → отчёт → статья; составной вид; конфликт Git; статья на двоих с общей базой.
- Чистая машина: установка → выбор папки с исследованиями → открытие проекта без ручного запуска сервера или редактирования конфигурации.
- Изменение принято, когда есть реализация, проверка, запись в этой спецификации (если контракт сдвинулся), пример и понятный откат.
